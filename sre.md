# SRE: как связать вопросы с книгой и практикой

SRE — инженерная работа над надёжностью сервиса. Для подготовки удобно разделить два масштаба: что происходит внутри Linux-машины и что происходит с сервисом, состоящим из многих машин и зависимостей.

Уорд хорошо объясняет первый масштаб. Поэтому его книга нужна для SRE, но **по ней одной нельзя подготовить ответы на всю SRE-подборку**. Нельзя выдавать главу о TCP за главу о балансировке, а главу о cron — за методику управления инцидентами.

Ниже карта [60 вопросов Тыльного](https://tylnyi.ru/sre-voprosy/) на 19 ноября 2026 года. Номера сгруппированы по учебным темам; каждый вопрос учтён. Это разбор покрытия и важных ограничений ответов, а не перепечатка банка вопросов. Страницы относятся к присланному русскому изданию Уорда: Питер, 2022, 3-е издание.

## Разбор ответов: что уточнять на собеседовании

В подборке полезна связь технических решений с последствиями для пользователя. Особенно стоит разбирать задачи на отказ зависимости, восстановление и измерения. Но пример решения не превращается в универсальное правило. Ниже уточнения к №4–5, 13, 22, 43 и 47–48.

### 1. Процент ошибок нельзя автоматически переводить в минуты

**Понятное объяснение.** Сначала определи, что считаешь: запросы или интервалы времени. В часы пик за минуту приходит больше запросов, чем ночью. Поэтому одинаковая длительность сбоя может испортить разную долю запросов.

**Пример.** Для учебного API выбран SLO 99,5% успешных запросов за 28 дней. За окно пришло 2 000 000 запросов. Разрешённый бюджет — 10 000 неуспешных запросов. Если их 4 000, израсходовано 40% бюджета. Перевести это в минуты без сведений о трафике нельзя.

**Короткий ответ.** «Сначала согласую индикатор, окно и условия успешного события; затем считаю бюджет в тех же единицах».

Основа и ограничения выбора SLI: [Google, Implementing SLOs](https://sre.google/workbook/implementing-slos/). У Уорда отдельной главы об этом нет.

### 2. Ключ повтора — ещё не полная защита от дублей

**Понятное объяснение.** Идемпотентность означает, что повтор той же операции не создаёт дополнительного эффекта. Одного сохранения ключа в Redis недостаточно, если запись результата в другую базу происходит отдельно и процесс может упасть между шагами.

**Пример.** Сервер отметил ключ как использованный, затем упал до создания заказа. Повтор теперь блокируется, хотя заказа нет. При обратном порядке можно получить два заказа. Нужно связать регистрацию операции с изменением состояния: например, транзакцией в одной базе. Для внешнего платежа нужны гарантии самого провайдера и сверка результата.

**Короткий ответ.** «Проверю не только уникальность ключа, но и атомарность эффекта, поведение после сбоя и срок хранения результата». Атомарность — выполнение связанных изменений целиком либо невыполнение всех этих изменений.

Первичный материал: [AWS, Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/). Книга Уорда этого не покрывает.

### 3. Скорость расхода бюджета требует правильных единиц

Burn rate — отношение текущей доли плохих событий к допустимой доле. Для предыдущего примера допустимо 0,5%. Если сейчас ошибочны 2% запросов, burn rate равен 4. Это не означает, что уже потрачено 400% месячного бюджета: значение характеризует темп, а не итог за окно.

Для запросного SLO время до исчерпания зависит ещё и от интенсивности трафика. Правило «окно разделить на burn rate» — оценка при соответствующих предположениях о трафике и доступном бюджете. Оповещение должно учитывать длительность ухудшения, объём наблюдений и необходимость действия.

Источник: [Google, Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/). Уорд помогает получить показатели CPU и памяти, но не описывает этот расчёт.

### 4. Добавление реплик само по себе не доказывает устойчивость

Это проверочный мысленный эксперимент для ответов о масштабировании. Есть четыре одинаковых экземпляра API, но все используют единственную базу. Удаление одного API может пройти незаметно; отказ базы остановит все четыре. Значит, проверять надо весь путь запроса.

Арифметика запаса тоже имеет условия. Пусть три равные зоны имеют по 120 единиц проверенной мощности. После потери одной останется 240. Нагрузка 210 помещается в этот предел, но это ещё не проверка времени переключения, состояния данных и ограничений сети. Утверждение об устойчивости подтверждают испытанием выбранного сценария. Для постановки таких задач см. SRE Workbook, главы 11–12 и 17, по [оглавлению](https://sre.google/workbook/table-of-contents/).

## Твоя первая практика по SRE

Возьми один учебный сервис: например, API заметок с базой данных. Не нужен Kubernetes, чтобы начать рассуждать о надёжности.

1. Нарисуй путь запроса: клиент → API → база. Для каждой стрелки напиши, что будет при отказе и при медленном ответе.
2. Определи один SLI: например, долю успешно сохранённых заметок. Запиши, где измеряешь результат и какие события исключаешь из знаменателя.
3. Выбери учебный SLO и окно. Посчитай бюджет на конкретном количестве запросов.
4. Смоделируй потерю ответа после сохранения. Объясни, как клиент узнает результат и не создаст вторую заметку.
5. Составь инструкцию на одну неисправность: симптом, команды проверки, ожидаемый результат, действие, условие остановки и проверка восстановления.
6. После эксперимента запиши, почему он произошёл и какое изменение позволит обнаружить или предотвратить повторение.

Для команд внутри машины возвращайся к [linux.md](linux.md), для порядка чтения — к [reading-plan.md](reading-plan.md). SRE добавляй после уверенного разбора процесса, службы, диска и сетевого соединения.
